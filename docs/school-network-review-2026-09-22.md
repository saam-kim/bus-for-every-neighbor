# Chrome·Edge 및 학교 네트워크 검토

검토일: 2026-09-22

대상: https://temporary-prompt-poplar-ezg5yq8.vercel.app/

## 판단

최신 Chrome·Edge를 사용하는 것 자체보다, 학교망의 외부 서비스 차단·불안정한 연결·공유 IP·동시 접속 규모가 주요 위험이다. 현재 일반 인터넷에서는 수업 생성, 학생 참여, 교사 진행 명령 전달이 정상 동작했다. 그러나 연결 장애를 알아차리고 복구하는 화면이 부족하므로, 학교망에서 무조건 안정적으로 된다고 안내할 단계는 아니다.

이번 작업은 검토와 대응 설계이다. 서비스 코드·Firebase 설정·요금제·배포는 변경하지 않았다.

## 실제 확인 범위

- 배포본의 `main.js`, `classroom.js`, `classroom-sync.js`와 로컬 파일을 비교했다. 줄바꿈을 제외한 내용이 모두 같았다.
- Codex 내장 브라우저에서 점검용 새 수업을 만들었다. QR 이미지 로딩(420px), 학생 모둠 입장, 교사 대시보드의 모둠 표시, 수업 시작 명령이 학생 화면에 전달되는 것을 확인했다.
- 같은 브라우저 프로필의 두 탭으로 확인했다. 서로 다른 기기·계정 간 동시 접속 부하 시험은 아니다.
- 동기화 큐에 서버 응답이 보류되는 상황과 명시적으로 실패하는 상황을 주입하는 Node 단위 테스트를 실행했다. 실제 방화벽을 차단한 테스트는 아니다.
- Chrome 연결을 시도했으나 자동 조작 가능한 Chrome이 없었다. Edge도 연결된 브라우저 목록에 없었다. 따라서 이번 검토에서 실제 Chrome·Edge 실행을 완료했다고 주장하지 않는다.
- 실제 학교 Wi-Fi, 교육청 보안 프록시, 관리형 브라우저 정책, 프로젝트의 현재 Firebase 요금제·여유 할당량은 미확인이다.

재현 파일: `tmp/school-network-audit.mjs`, 결과: `tmp/school-network-audit-results.json`.

동기화 테스트에서 확인한 정상 동작도 있다. 명시적으로 거절된 전송은 실패를 알렸고 이후 재시도로 성공했다. 앞선 전송 응답이 돌아오면 대기 중이던 최신 수정 내용도 이어서 전송했다. 문제는 연결 보류 중의 가시성과 복구 안내이지, 모든 수정이 즉시 사라진다는 뜻은 아니다.

## 저장·복구의 한계

학생의 설계와 기록은 별도로 localStorage에 저장한다. 같은 기기·같은 브라우저를 유지하고 저장 공간을 사용할 수 있다면 복구에 도움이 된다. 다만 수업 재입장은 다시 서버 조회를 필요로 하므로, 연결이 끊긴 상태에서 새로고침하면 바로 활동을 재개할 수 있다고 보장할 수 없다.

Firebase 웹 SDK의 미전송 큐 자체는 브라우저 세션 밖에 영구 보존되지 않는다. 로컬 저장 성공과 교사 화면 전송 성공을 분리해서 표시해야 한다. 교사 명령도 로컬 이벤트 때문에 먼저 반영되어 보일 수 있으므로 서버 확인 전에는 ‘전달 완료’로 취급하면 안 된다.

관리형 브라우저가 사이트 저장을 차단하거나 종료 시 데이터를 지우면 익명 사용자 식별과 기록 복구가 영향을 받는다. 특히 교사가 Chrome에서 만든 수업을 Edge에서 열거나 브라우저 데이터를 지우면 같은 교사 권한이 자동으로 이어지지 않는다. 장애 해결책으로 캐시·사이트 데이터 삭제를 먼저 권하지 않는다.

## 여러 교사가 공유해서 사용할 때

Firebase 공식 문서상 새 계정 생성 제한은 IP 주소당 시간당 100개이다. 이 앱의 익명 인증도 신규 계정을 만들 수 있으므로, 학교가 하나의 외부 IP를 공유하고 여러 학급이 처음 접속하면 영향을 받을 수 있다. 기존 익명 사용자의 재사용은 매번 새 계정을 만드는 것과 다르다. 시크릿 창·사이트 데이터 삭제로 해결하려 하면 신규 생성이 더 늘 수 있다.

Realtime Database의 Spark 요금제는 데이터베이스 전체에서 동시 연결 100개 제한이 있다. 수업 코드마다 100개가 아니다. 현재 프로젝트의 요금제는 확인하지 않았으므로 실제 한도가 100개라고 단정하지 않는다. 교사 공유 전에 요금제, 피크 연결 수, 사용량을 확인하고 필요할 때 운영자가 할당량·비용을 검토해야 한다. 임의 요금제 변경은 하지 않았다.

## 학교 전산 담당자와 확인할 접속 대상

학교의 허용 정책에 따라 아래 서비스를 점검한다. 브라우저 보안 경고나 인증서 검증을 우회하는 방법은 해결책으로 사용하지 않는다.

| 대상 | 용도 |
| --- | --- |
| `temporary-prompt-poplar-ezg5yq8.vercel.app` | 앱·지도·글꼴·인쇄 자료 |
| `www.gstatic.com`의 `/firebasejs/` | 현재 Firebase SDK 다운로드 |
| `identitytoolkit.googleapis.com`, `securetoken.googleapis.com` | Firebase 인증·토큰 갱신용 API |
| `bus-every-neighbor-20260914b-default-rtdb.asia-southeast1.firebasedatabase.app` | 수업·모둠 실시간 데이터 |
| `api.qrserver.com` | 현재 QR 이미지 생성; 차단되어도 직접 주소 입장은 별도 가능 |

이는 주요 접속 대상이며 모든 리디렉션·전송 호스트를 포괄하는 확정 허용 목록은 아니다. 실제 학교망의 실패 요청 로그로 필요한 대상과 장기 연결 허용 여부를 좁혀 확인한다. 단순히 첫 페이지가 열리는 것만으로 인증·DB 연결을 정상 판정하지 않는다.

## 교사용 최소 사전 점검과 당일 대응

1. 수업 때 사용할 학교 Wi-Fi에서 교사 기기와 학생 기기 한 대로 점검한다. 교사망·학생망이 다르면 각각 실제 사용할 망을 쓴다.
2. 새 수업 생성 → 학생 QR 또는 주소 입장 → 대시보드 모둠 표시를 확인한다.
3. 교사가 수업을 시작하고, 학생의 설계 변경·운행 결과가 교사 화면에 실제 도착하는지 확인한다. 인쇄와 주소 복사도 한 번 확인한다.
4. 학생 기기의 연결을 잠시 끊었다가 복구해 로컬 수정 내용과 교사에게 도착한 결과를 비교한다. 미전송 중에는 창을 닫거나 사이트 데이터를 지우지 않는다.
5. QR만 안 보이면 화면의 접속 주소 `/#join`과 6자리 코드를 사용한다. 주소 복사가 정책상 막혔으면 주소를 직접 입력한다.
6. 화면은 열리지만 입장·전송이 안 되면 전산 담당자에게 인증·DB 접속을 확인 요청한다. ‘인터넷 연결됨’만으로 Firebase 연결까지 확인된 것은 아니다.
7. 실시간 연결을 해결하지 못했으나 앱 파일은 열 수 있다면 [활동 미리보기](https://temporary-prompt-poplar-ezg5yq8.vercel.app/#play)와 인쇄 활동지로 독립 활동을 진행할 수 있다. 이 경로는 교사 대시보드에 결과를 보내지 않으며, 기존 세션 기록을 자동으로 옮기지 않는다. 사이트 자체가 차단된 경우에는 해결책이 아니다.

## 구현 순서 제안

1. 연결·전송 상태를 정확하게 표시하고, 무한 대기 대신 재시도 안내를 제공한다.
2. QR 자체 생성과 Firebase SDK의 앱 내 배포로 차단 지점을 줄인다.
3. ‘수업 전 연결 점검’에서 저장 가능 여부, 인증, DB 연결·응답을 확인한다. 결과에는 점검한 시각과 당시 기기만 검증했다는 범위를 표시한다.
4. 학생 구독 범위와 이미지 크기를 줄인다.
5. 마지막으로 실제 학교망에서 Chrome·Edge 각각 최소 사전 점검을 수행하고, 학교별 허용 정책과 프로젝트의 동시 접속 여유를 확인한다.
